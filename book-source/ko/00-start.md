# 00장. Wickle 0.2.0까지 만드는 학습 경로

Rust·에이전트의 기초를 먼저 익히는 장이다. 최종 구현 목표는 0.2.0이며 03–36장의 기초 구현과 37–60장의 개선 과정을 차례로 진행한다.

[목차](README.md) · [다음: Rust 기초](01-rust.md)

## 완성할 프로그램

“이 workspace의 보고서를 찾아 요약해 줘”라는 요청을 받는 Host를 생각하자. 모델은 검색 도구를 제안하고, 엔진은 모델이 준 검색어에 Host가 인증한 workspace 값을 붙인다. 현재 권한을 검사하고 검색 결과를 저장한 다음 모델에 관찰값을 돌려준다. 쓰기 작업이라면 승인과 외부 효과 확인도 필요하다. 프로세스가 죽어도 이미 수행한 쓰기를 무턱대고 다시 하면 안 된다.

이런 실행을 담당하는 **Rust 라이브러리 Wickle 0.2.0**을 만든다. 노코드 관리 화면, 계정 서버, SaaS 배포, 자체 모델 학습을 구현하는 과정은 아니다. 그것들은 이 라이브러리를 사용하는 Host 제품의 영역이다. 전체 구현을 마치면 코어, SQLite, 모델 라우터, 어댑터 조립, 제공 경로 7종, MCP를 포함한 13개 crate가 완성된다.

최종 기준은 Git tag `v0.2.0`, commit `b1416772dd185a3b175db6e3099512d9006f48f5`다. 03–36장은 기존 0.1.0 기반을 만드는 중간 단계다. 지금의 main이나 최신 API로 임의 업데이트하지 않는다. 지원 범위는 그 release 코드가 기준이다. 교재의 아키텍처 평가는 코드에서 도출한 설명이며, 별도 근거가 없는 저자의 역사적 의사결정을 인용한 것은 아니다.

## 에이전트를 처음 배운다면

LLM은 입력 문맥을 받아 텍스트나 구조화된 출력을 생성하는 모델이다. 입력과 출력은 token이라는 처리 단위로 계산된다. token은 글자 수나 UTF-8 byte 수와 같지 않다. 모델에 한 번 요청하는 일을 inference라고 한다. 이 교재는 모델을 학습시키는 과정이 아니라 이미 제공되는 모델을 소프트웨어 구성요소로 사용하는 과정이다.

단순 채팅 프로그램은 사용자 문장을 모델에 보내고 응답을 보여 준다. 에이전트는 그 응답이 도구 사용 제안이면 도구를 실행하고, 관찰한 결과를 다시 모델에 제공하며 다음 행동을 결정하게 한다. 이를 agent loop라고 부른다. Wickle에서는 모델이 스스로 운영체제를 제어하지 않는다. 실제 실행은 Host가 등록한 ToolExecutor와 core의 검사 경로가 담당한다.

예를 들어 모델이 `search_report`에 `{"query":"지난달 매출"}`을 제안하면, Host가 인증한 workspace 값을 binder가 추가하고 권한을 확인한다. 도구가 반환한 검색 결과는 다음 모델 요청의 관찰값이 된다. 모델이 “게시하겠습니다”라고 말하는 것과 실제 게시 도구가 성공한 것은 별개다. 이 차이를 기록하는 것이 상태와 효과 원장의 역할이다.

대화를 이어가는 것처럼 보여도 모델 호출에 제공하지 않은 과거 자료를 자동으로 기억한다고 가정하지 않는다. Host가 저장한 transcript에서 필요한 부분을 골라 다시 보내거나, 특정 제공자의 continuation 계약을 사용한다. 긴 context는 비용과 한도가 있으므로 검색·선택·압축이 필요하다. context를 늘리는 것과 모델이 근거를 정확하게 이해하는 것도 같은 보장이 아니다.

검색된 자료를 함께 보내는 방식이 RAG다. ContextSource는 이런 읽기 자료를 자동 조회한다. Skill은 “어떤 순서로 업무를 수행할지”에 관한 버전 있는 지시 본문이고, Tool은 실제 조회·계산·업무 변경을 수행하는 코드다. Memory는 과거 관찰을 나중에 읽을 수 있게 저장한 외부 자료일 수 있다. 이들은 모두 모델 자체를 다시 학습시키는 것과 구별한다.

에이전트는 반드시 끝나는 조건이 있어야 한다. 모델이 더 이상 도구를 제안하지 않는 것, 형식 검사를 통과하는 것, 업무 검증을 통과하는 것, 사람의 승인이 필요한 것, 시간·호출 예산이 끝난 것을 각각 다른 결과로 다룬다. 무제한 `while true`로 모델과 도구를 반복하는 프로그램은 이 요구를 충족하지 못한다.

처음에는 실제 LLM 대신 정해진 event를 내는 ScriptedModel을 쓴다. 그래야 특정 순간에 오류·도구 제안·완료를 재현하여 엔진의 결함을 찾을 수 있다. 이런 테스트는 모델이 사람의 요청을 잘 이해하는지 평가하는 실험과 목적이 다르다. 실제 모델의 응답 품질 검사는 추가 평가 과제로 분리한다.

## 선수 지식과 학습 방식

함수·조건문·반복문·자료구조, 프로세스와 스레드, HTTP 요청/응답, DB 트랜잭션의 기초를 안다고 가정한다. Rust와 에이전트는 처음이어도 된다. 익숙하지 않은 용어는 [용어집](glossary.md)을 먼저 읽는다.

1. 본문의 문제를 읽고 결과를 먼저 예측한다.
2. Rust Book의 지정 장과 짧은 예제를 실행한다.
3. 해당 단계의 테스트 입력·기대값을 읽고 구현한다.
4. 막히면 전체 구현 문서에서 해당 함수까지 읽고 다시 직접 작성한다.
5. 테스트에 통과하면 의도적인 결함을 넣어 실패하는지 확인한다.
6. 왜 이런 경계가 필요한지, 더 단순한 대안의 비용은 무엇인지 설명한다.

정답 패치를 적용하는 것은 실습 환경을 복원하는 방법이다. 적용만 하고 테스트가 초록색인 것을 이해했다고 평가하지 않는다. 각 장의 질문에 답하고 실패 사례를 재현하는 것이 학습의 일부다. 중간 단계의 API는 점차 확장되므로 60장 파일을 08장이나 43장에 섞지 않는다.

## 1. 도구 준비

macOS 또는 Linux, Git, Python 3.9 이상, Rustup과 Rust toolchain, C/C++ 빌드 도구가 필요하다. SQLite는 bundled로 컴파일하므로 C 빌드 환경을 사용한다. MCP 테스트의 로컬 서버 fixture는 Python을 사용한다. 이 과정은 Windows에서 검증하지 않았다.

Rust 설치는 [Rust Book 1장](https://doc.rust-lang.org/book/ch01-01-installation.html)을 따른다. 처음 다운로드와 Cargo dependency 설치에는 네트워크가 필요하다. 이후 기본 검증은 로컬 fixture를 사용하며 유료 모델 API key는 필요하지 않다.

```sh
rustup toolchain install 1.98.1 --profile minimal --component rustfmt --component clippy
rustc +1.98.1 --version
cargo +1.98.1 --version
python3 --version
git --version
```

기대 결과는 각 도구의 버전 출력이며 rustc는 `1.98.1`이다. Wickle 코어의 MSRV는 1.85지만 이 교재의 개발·재현 환경은 저장소에 고정된 1.98.1을 사용한다. 현재 온라인 Book의 요구 버전과 MSRV가 다르다고 dependency 버전을 임의로 바꾸지 않는다.

### 디스크와 빌드 캐시

여러 checkpoint를 차례로 컴파일하면 Cargo의 `target` 캐시가 수 GB 이상으로 커질 수 있다. 교재 검증 중에도 누적 캐시로 디스크가 부족해지는 상황을 확인했다. 특히 package 검사는 별도 위치에서 여러 실행 파일을 만든다. 링크 단계의 `No space left on device`는 Rust 코드 오류와 다르다.

실습 폴더에서 `cargo clean`은 해당 workspace의 생성된 빌드 산출물을 제거한다. 소스와 교재를 지우는 명령이 아니다. 다만 다음 빌드는 다시 컴파일하므로 시간이 걸린다. 다른 빌드가 실행 중일 때 같은 target을 정리하지 않는다. 용량을 줄이되 기본 debug 검증을 유지하려면 incremental cache를 끈다.

```sh
export CARGO_INCREMENTAL=0
```

반복 컴파일 속도 일부를 포기하지만 debug 정보와 기본 stack 조건은 유지한다. 0.2.0 변경 기록에 실제 기본 debug 스택 결함이 있었으므로 debug=0이나 큰 RUST_MIN_STACK을 통과 기준으로 사용하지 않는다.

## 2. 교재와 실습 폴더 분리

이 문서가 있는 `ko/` 폴더에서 실행한다. 저장 위치는 `CONTEXT/wickle/learning/v0.2.0/ko/`이며, 압축본을 풀었다면 그 안의 `ko/` 폴더를 사용한다. 이후 명령은 bash/zsh 기준이다. 함께 제공하는 `../reference/`는 최종 0.2.0, `../reference-v0.1.0/`은 기초 완성본이다. 실습은 새 폴더에서 진행한다.

```sh
export COURSE="$PWD"
python3 "$COURSE/lab.py" list
mkdir ../wickle-lab
cd ../wickle-lab
git init
```

`list`는 03–60장의 checkpoint 목록을 출력한다. `wickle-lab`이 이미 있으면 다른 새 이름을 사용한다. 교재 checkout과 실습 폴더를 동일하게 두지 않는다. 새 터미널을 열면 `COURSE`를 교재의 실제 절대 경로로 다시 설정한다. Python helper는 교재 자체의 위치를 기준으로 자료를 읽으므로 현재 Git checkout의 branch/history는 필요 없다.

## 3. 첫 결과 보기

Wickle 코드를 쓰기 전에 독립적인 Rust 예제를 실행해 컴파일 환경을 확인한다.

```sh
rustc +1.98.1 --edition=2024 "$COURSE/examples/ownership.rs" -o /tmp/wickle-ownership
/tmp/wickle-ownership
```

기대 출력:

```text
request: report
shared owners: 2
```

이제 [01장](01-rust.md)의 코드 해설을 읽는다. 03장의 workspace 설정은 이 `wickle-lab` 안에 작성한다. 기초 연습 예제는 교재 `examples/`에 별도로 있으며 실제 Wickle public API라고 혼동하지 않는다.

## 정답과 검증 도구의 역할

| 자료 | 용도 |
| --- | --- |
| 각 장 `.md` | 개념, 설계 이유, 구현 순서, 결함 실험과 해설 |
| `implementation/NN-*.md` | 그 단계에서 바뀐 모든 Rust 파일의 생략 없는 완성 코드 |
| `solutions/NN-*.patch` | 이전 단계에서 다음 단계로 가는 전체 변경; manifest/lockfile도 포함 |
| `course.json` | 고정 commit, patch checksum, 참조 파일 checksum, 장별 테스트 명령 |
| `lab.py snapshot NN --dest 새폴더` | 빈 폴더에 03장부터 누적 복원; 기존 폴더를 덮어쓰지 않음 |
| `lab.py compare NN --work 실습폴더` | 참조에 있는 파일의 byte 차이 확인; 추가 학습 파일은 검사하지 않음 |
| `lab.py check NN --work 실습폴더` | 해당 장에 지정된 실제 Rust 테스트 실행 |

완성본이 먼저 필요하면 `python3 "$COURSE/lab.py" snapshot 60 --dest ../wickle-reference`를 실행한다. GitHub에 접속하거나 Git history를 다운로드하지 않아도 교재 안의 패치만으로 전체 release가 복원된다. 단, 패치 checksum은 자료 손상 검출용이지 신뢰할 수 없는 교재의 실행 안전성을 증명하는 전자서명이 아니다.

## 예상 분량

대학 강의와 자습을 합쳐 한 학기 이상을 생각하는 편이 적절하다. 01–02장은 Rust 기초, 03–14장은 엔진 기반, 15–24장은 실행·확장·복구, 25–32장은 통신 어댑터, 33–36장은 통합과 배포다. 장당 소요 시간은 기존 Rust 경험과 직접 작성하는 범위에 따라 크게 달라진다. 모든 코드를 한 번에 암기하는 대신 같은 불변 조건이 여러 경계에서 반복되는 이유를 이해한다.

## 0.1.0 학습을 마쳤다면

[37장](37-compatibility.md)부터 진행한다. 자신의 0.1.0 코드가 있다면 보존하고 36번 snapshot과 차이를 확인한 뒤 적용한다. 완전한 새 학습자는 00장부터 60장까지 따른다. 0.2.0은 내부 계약 변경을 포함하므로 버전 문자열만 바꾸거나 0.1.0 active DB에 바로 새 바이너리를 연결하지 않는다. [변경 지도](changes-v0.2.md)와 [이관 실습](migration-lab.md)을 읽는다.
